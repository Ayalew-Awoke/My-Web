“”””””””Design and Implementation of RAG Based Legal Document Assistant System Using LLM For Ethiopia Amharic Language
The Challenge
Millions of Amharic speakers lack access to legal information. Legal documents are complex, written in formal language, and no intelligent tools exist to help citizens understand their rights. Traditional search fails completely—it doesn't understand meaning, only keywords.
The Solution
I built an AI-powered legal assistant that understands questions in Amharic and retrieves accurate answers directly from Ethiopian law documents. The system combines three powerful search methods to find the most relevant legal information, then generates clear answers in Amharic.
What I Built
Backend Engine (Python + FastAPI)
Processes Amharic queries and generates embeddings
Coordinates hybrid search (dense + sparse + reranking)
Prevents false answers through context-grounding
Intelligent Retrieval System
Dense semantic search (understands meaning)
Sparse keyword search (matches exact terms)
Neural reranking (picks the best results)
Vector database with 2,345 legal document chunks
Large Language Model Integration
Generates accurate Amharic responses
Refuses to answer when information is unavailable
Grounded in verified legal documents only
User Interface
Clean, responsive chatbot
Proper Amharic/Ethiopic script support
Real-time responses
User authentication & history
How It Works
User Question (Amharic)
    ↓
Query Processing (Unicode normalization)
    ↓
Hybrid Search
├─ Find semantic meaning matches (30%)
├─ Find exact term matches (30%)
└─ Re-rank top results (40%)
    ↓
Retrieved Legal Context
    ↓
Generate Answer (LLaMA via GROQ)
    ↓
User Gets Amharic Answer
Key Innovation: Hybrid Retrieval
Most systems use only one search method. I combined three:
Dense Search: Understands "What are bail requirements?" even if phrased differently
Sparse Search: Finds exact matches like "bail," "article 49"
Rank Fusion: Combines both to maximize accuracy
Result: Better coverage for legal queries that need both semantic understanding AND precision.

Finetuning Automatic Speech Recognition (ASR) System for Amharic Language(Information Network Security Administration (INSA)) Internship Project
The Challenge
Amharic is spoken by tens of millions of people, yet speech recognition technology for it remains far behind English and other high-resource languages. Existing ASR systems are built and optimized for languages with massive labeled datasets — Amharic has neither the data volume nor the research attention. Add in accent variation, background noise, and Amharic's rich morphology, and most modern ASR models simply fail to produce usable transcriptions.
The Solution
We fine-tuned two state-of-the-art ASR architectures — Wav2Vec2 and Whisper — on a custom-built Amharic speech dataset, adapting each model's internal representations to Amharic's acoustic and linguistic patterns. Rather than building a model from scratch, we leveraged transfer learning to make pre-trained multilingual/self-supervised models understand Amharic speech accurately.
What We Built
Data Pipeline
Collected Amharic speech data from INSA's CAC dataset and YouTube (news, interviews, parliamentary recordings)
Built a custom audio cutter to segment long recordings into ~30-second clips
Standardized all audio to 16kHz WAV format with aligned transcriptions and metadata
Audio Preprocessing
Noise reduction and amplitude normalization
Waveform-to-array conversion for model input
Speaker-diverse dataset to improve generalization to unseen voices
Model Fine-Tuning
Wav2Vec2: fine-tuned using CTC loss for direct audio-to-text alignment
Whisper: fine-tuned using sequence-to-sequence training for encoder-decoder transcription
Both trained and evaluated on the same Amharic dataset for direct comparison
Evaluation Framework
Word Error Rate (WER) and Character Error Rate (CER) scoring
Testing under both clean and noisy audio conditions
How It Works
Speech Data Collection (YouTube + CAC dataset)
    ↓
Audio Extraction (WAV format)
    ↓
Audio Segmentation (30-sec clips) + Preprocessing
    ↓
Feature Extraction (Wav2Vec2 / Whisper processors)
    ↓
Model Training & Fine-Tuning (CTC loss / Seq2Seq loss)
    ↓
Comparative Evaluation (WER & CER)
    ↓
Amharic Text Output
Key Innovation: Dual-Model Comparative Fine-Tuning
Instead of committing to a single architecture, we fine-tuned and evaluated two fundamentally different ASR paradigms side by side:
Wav2Vec2 — self-supervised, CTC-based, lightweight to fine-tune, efficient on limited hardware
Whisper — multilingual, encoder-decoder, pre-trained on diverse noisy real-world audio
Result: Whisper consistently outperformed Wav2Vec2 on both WER and CER, and showed far greater robustness to noisy recordings — largely due to its large-scale multilingual pretraining. This comparison gives a clear, evidence-based answer to "which architecture should low-resource language projects start with."

Why It Matters
Direct comparison, not just implementation — gives future Amharic ASR work concrete evidence on which model architecture to prioritize
Real-world data — built from actual Amharic broadcasts, interviews, and parliamentary speech, not synthetic data
Foundation for accessibility tools — supports future voice assistants, transcription services, and accessibility technology for Amharic speakers
Applicable beyond Amharic — the same fine-tuning and evaluation pipeline can be extended to other low-resource Ethiopian languages (Oromiffa, Tigrinya, etc.)
What We Learned
🔹 Whisper's multilingual pretraining gives it a real edge in low-resource, noisy conditions🔹 Wav2Vec2 is more compute-efficient to fine-tune but more sensitive to dataset quality/noise🔹 Both models were undertrained at only 10 epochs — results likely understate their true potential🔹 Audio segmentation and alignment quality directly determine transcription accuracy🔹 Compute availability (GPU access) is a real bottleneck for low-resource language ASR research
Next Steps
→ Train both models for significantly more epochs (500+) with dedicated GPU resources→ Expand and diversify the Amharic speech dataset→ Improve noise reduction and preprocessing pipelines→ Explore multilingual ASR models covering multiple Ethiopian languages→ Optimize models for real-time, low-resource deployment

Tour ticket Reservation system for gondar
Project Overview
✦ The Challenge
Gondar is one of Ethiopia's most historically significant cities, home to the UNESCO-listed Fasil Ghebbi (Royal Enclosure)
Tourist ticketing was still entirely manual — paper-based sales, registration, and reporting
Long queues during peak seasons like Timkat
Frequent data-entry errors and lost/damaged records
Poor coordination between attraction managers, vendors, and tourism offices
No visibility into visitor trends or sales data for decision-making
Tourists had no way to book ahead or pay online
◆ The Concept
Replace the manual workflow with a centralized, web-based reservation platform
Let tourists browse attractions, book tickets, and pay online in one place
Give administrators full control over inventory, users, and reporting from a single dashboard
Scope the system around two roles: Tourist and System Admin
Build role-based access control as the backbone of the design
◈ What We Built
As a team of four, we designed and developed a full-stack Tour Ticket Reservation System (TTRS) using PHP, MySQL, HTML, CSS, and JavaScript.
Tourist side:
Registration and login
Browsing tour packages with details and pricing
Booking tickets with date selection
Secure online payment via Chapa
Viewing booking/tour history
Profile management
Feedback submission
Admin side:
Managing attractions and packages
Confirming and tracking bookings
Managing users
Generating reports and statistics
Payments:
Integrated Chapa gateway for real-time transaction confirmation
Digital receipts
Automated SMS/email confirmations
⬡ How It Works
Modular architecture built around seven core components: 
Authentication Module
Attraction Management Module
Booking Engine
Payment Processing Module
Reporting Module
Notification Service
Search and Filter Module
Booking flow: tourist selects a tour → submits booking request → Booking Controller checks availability → booking record + ID generated → hands off to Payment Module → payment succeeds → status updates to "Confirmed" → SMS/email confirmation sent
Admin flow: request submitted → system authenticates admin → backend processes request → database updated/queried → response returned to admin
Relational database (MySQL) normalized around four core tables: User, Ticket, Booking, and Payment, linked by foreign keys
✧ Technology & Craft
Frontend: HTML, CSS, JavaScript, Bootstrap (responsive design)
Backend: PHP for server-side logic
Database: MySQL, tested locally via XAMPP/Apache
Payment: Chapa payment gateway

Methodology: Agile development with iterative testing and constant communication with our advisor
Design/Analysis: UML modeling — use case, object/block, sequence, and activity diagrams
Security: Role-based access control, hashed passwords (bcrypt), input validation and sanitization against SQL injection and XSS
➤ Outcome & Insight
Successfully automated ticket browsing, booking, and payment processes
Gave admins centralized control over inventory and reporting
Functional testing showed reliable data handling and a smooth, mobile-responsive interface
Overcame challenges with real-time inventory updates and payment gateway integration through iterative testing and team debugging
Deepened our understanding of how costly manual, paper-based tourism operations are in time, accuracy, and visitor experience
Confirmed that a modest tech stack (PHP/MySQL/Chapa) can meaningfully modernize ticketing for a heritage destination
Future improvements identified: 
QR-code ticket scanning at entrances
Two-factor authentication
Native Android/iOS mobile app
